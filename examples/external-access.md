# Fictional external-reference and access cases

These cases specify expected behavior for a private deployment. They do not install access controls or claim that a connector, backend, or live permission change has been tested.

## Working documents stay at source

A fictional studio has three selected documents:

| Source | Location | Enabled use and audience |
| --- | --- | --- |
| Equipment checklist | A technician's working folder | Reference only; the technician permits its title and locator in the team brain. No permission to read or distill its body. |
| Project schedule | An existing shared document service | Live consultation for project members. Answer delivery is permitted in the private project session; no durable integration is granted. |
| Leadership planning record | A restricted document collection | Leadership-only discovery, reading, and integration. An authorized background identity may update the restricted leadership brain automatically. |

No document is moved. The original folder's other files are outside scope. If another machine cannot resolve the technician's path, it records that limit instead of assuming the file is absent or scanning other folders.

## Derived visibility

The leadership source supports a confidential budget decision. The agent saves its decision note and receipt only in enforced leadership storage. A general team home, index, activity report, or context pack must not expose the decision, source title, or its existence.

An answer combining that record with a team-readable project schedule remains subject to both sources' restrictions and may be delivered only in a session allowed by both grants. The schedule's consultation-only grant does not permit saving that combination as a durable note. A connector account that can read both does not authorize showing the answer to every project member.

Leadership separately authorizes publishing one statement: "The existing equipment budget remains in effect this month." The agent can place that statement in the team brain under the recorded release grant. Removing names from the whole planning record would not authorize publishing it. A standing release policy may support automatic future statements within its bounds.

## Revocation and missing access

When a member loses leadership access, future requests must not return the protected note through direct reading, search snippets, an old context pack, or a cached answer. The deployment must check or invalidate managed derivatives under its policy. If current authorization cannot be verified, it withholds affected output.

This does not prove that the budget decision became false. Nor does it erase a document that the member already downloaded, historical Git objects already served, or an answer already loaded in an agent session. State these limits and apply the environment's available history, session, cache, and retention controls. An independently authorized team statement is reviewed under its own release policy rather than deleted automatically.

## Deployment checks

Use disposable identities and invented content to test the actual configured boundary:

1. Register the equipment reference without reading its body or marking its content integrated. Deny an ingestion request lacking a new integration grant.
2. Answer a permitted live project question without saving an unauthorized lasting note or copying it to a wider conversation.
3. Ask as a team member for leadership material. The environment must withhold it before the model receives content or revealing metadata. A prompt asking the model to ignore already loaded secrets is not a passing check.
4. Run the privileged ingestion and confirm that its notes, receipts, packs, and searchable outputs remain restricted despite its broader source access.
5. Combine sources with different audiences in a permitted answer, or obtain a separate integration grant before saving a combination. Verify that all applicable disclosure and retention restrictions remain. Test an authorized narrow release separately from an unauthorized broader summary.
6. Change a disposable membership without changing source text. Exercise fresh reading, search, packs, and managed caches; report previously distributed-copy limits separately.

An agent's reasoning walkthrough establishes only instruction behavior. A backend claiming enforcement needs positive and negative tests against its real delivery paths.
